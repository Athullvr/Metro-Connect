# Metro Connect — Remaining Work (Phases 3–6)

This document exists so any coding assistant (or human) picking this project up — without access to prior conversation history — can understand what's already built, why, and exactly what's left to do. Work through the phases **in order**; each phase assumes the previous ones are solid. Don't skip ahead.

## What this project is

Metro Connect is a mobile-first PWA that plans multimodal transit journeys across Kochi's Metro (Blue Line), Water Metro, and feeder e-buses — plus a "Copilot" reasoning layer that can explain route choices and reroute around disruptions. It's positioned as a differentiated alternative to generic map apps, which barely cover Kochi's Water Metro/feeder network.

Stack: React 19 + Vite 8 + Tailwind 4, deployed as a static site + Vercel serverless functions.

## What's already done (Phases 1–2)

**Phase 1 — Security.** OpenAI calls no longer happen client-side. `api/plan.js` and `api/replan.js` are Vercel serverless functions that hold `OPENAI_API_KEY` server-side (read in `api/_lib/callOpenAI.js`, 15s timeout) and proxy planner/adapter requests. The frontend (`src/services/openai.js`) calls `/api/plan` and `/api/replan` only — no API key ever reaches the browser, `localStorage`, or the bundle. Also fixed a critical issue where the repo had two disconnected implementations (a legacy static site and an orphaned React app that never mounted); the React app is now the one that actually ships (`index.html` → `src/main.jsx` → `App.jsx`).

**Phase 2 — Core planning logic.** The old ~140 lines of hardcoded if/else route matching (4 canned origin/destination pairs) are gone, replaced by a real graph engine:

- `src/data.json` — single source of truth for the transit network (metro stations, water metro jetties/routes, feeder buses, road links, walk connections, landmarks).
- `src/lib/transitGraph.js` — builds one deduplicated multimodal graph from `data.json`; Dijkstra shortest-path (`findShortestPath`) with constraint-weighted edges (speed/cost/scenic/luggage preferences) and node/route blocking (for disruption rerouting).
- `src/lib/routeFormatter.js` — converts a raw graph path into the `{legs, total_duration, total_cost, explanation}` shape the UI renders.
- `src/lib/stationMatcher.js` — fuzzy station/landmark name matching (exact → substring → Levenshtein distance), plus a small Malayalam alias set. Unresolved input throws `UnresolvedStationError` with suggestions instead of silently guessing.
- `src/lib/disruptionParser.js` — scans free-text disruption copy for known station/route names so rerouting works for any part of the network, not 3 fixed presets.
- `src/services/openai.js` — `getLocalPlannedRoute`/`getLocalReplannedRoute` now call the graph engine; `planRoute`/`replanRoute` (exported) still control simulator-vs-live-proxy switching same as before.
- Error states (`planError`, `replanError`) surface in `App.jsx` → `Home.jsx` / `DisruptionSimulator.jsx` so a bad station name or an unroutable disruption shows the user a real message instead of failing silently.

**Known open gap (not yet fixed):** `Eloor Jetty` is listed in `data.json`'s `water_metro.jetties` but has zero routes connecting to it — it's an unreachable node in the graph. No real-world route data was available to fix this without fabricating one; flagged for whoever picks this up next (Phase 5 is a natural place to revisit it, or address it standalone).

## Phase 3 — Reliability

**Goal:** the live-Copilot path (proxy → OpenAI) shouldn't be able to hang the UI or crash on a bad response.

1. **Client-side retry/backoff + timeout on the proxy fetch calls.** `src/services/openai.js`'s `planRoute`/`replanRoute` currently do a single `fetch('/api/plan', ...)` / `fetch('/api/replan', ...)` with no timeout and no retry. Add:
   - A timeout (e.g. `AbortController`, ~10-15s) so a hung request doesn't leave `loading` stuck true in `App.jsx` forever.
   - A small retry with backoff (e.g. 1 retry after a short delay) for transient failures (network blip, 502/503 from the proxy) — not for 4xx errors, which won't succeed on retry.
   - Note: `api/_lib/callOpenAI.js` already has a **server-side** 15s timeout on the OpenAI call itself (from Phase 1). This phase is about the **client's** fetch to `/api/plan`/`/api/replan`, which currently has no such protection.

2. **JSON-schema validation of LLM responses before rendering.** When `useSimulator` is false and the live proxy returns a response, `src/services/openai.js` currently does `return await response.json()` and hands it straight to `Itinerary.jsx`/`DisruptionSimulator.jsx`, which assume a well-formed `{legs, total_duration, total_cost, explanation}` shape. An LLM can return malformed or partially-wrong JSON. Add a validation step (a lightweight hand-rolled validator is fine — no need for a new dependency like `zod` unless you want one) that checks:
   - `legs` is a non-empty array
   - each leg has `mode` (one of `metro`/`water_metro`/`feeder_bus`/`walk`), `from`, `to`, `duration` (number), `cost` (number)
   - `total_duration`/`total_cost` are numbers
   
   On failure, throw a typed error (e.g. `InvalidResponseError`) and let the existing fallback-to-simulator logic in `planRoute`/`replanRoute` catch it and fall back — this reuses the pattern already in place for fetch failures.

**Acceptance check:** simulate a hung `/api/plan` (or a malformed JSON response) and confirm the UI recovers (falls back to simulator or shows an error) instead of spinning forever or throwing an unhandled exception in `Itinerary.jsx`.

## Phase 4 — Testing

**Goal:** the highest-regression-risk logic (graph pathfinding, fuzzy matching, disruption parsing, LLM response parsing) has unit test coverage. There is currently zero test infrastructure — no test script in `package.json`, no test files anywhere.

1. **Set up Vitest** (natural choice since this is a Vite project — shares its config/transform pipeline). Add `vitest` as a devDependency, add a `"test": "vitest run"` script to `package.json`.
   - Note: `src/lib/*.js` import `data.json` using the `with { type: 'json' }` import assertion syntax (added deliberately during Phase 2 so these modules could be exercised directly via plain `node` for manual verification). Confirm Vitest's Vite-based transform handles this without extra config — it should, but verify with a trivial test first before writing the full suite.

2. **Write unit tests for:**
   - `src/lib/transitGraph.js` — `findShortestPath` returns correct paths for known pairs (the 4 original demo routes are a good baseline — their expected costs are documented in the Phase 2 summary/commit history), returns `null` for disconnected/blocked-off pairs, respects `blockedNodeIds`/`blockedRouteIds`.
   - `src/lib/stationMatcher.js` — exact match, substring match, Levenshtein fuzzy match (typo tolerance), Malayalam alias resolution, and the "no match → suggestions" path.
   - `src/lib/disruptionParser.js` — the metro-vs-water-metro disambiguation logic in particular (this was a real bug found and fixed in Phase 2 — e.g. "Vyttila Water Metro Jetty is closed" must block only the jetty node, not the Vyttila metro station; a regression test here is high-value).
   - `src/services/openai.js` — `getLocalPlannedRoute`/`getLocalReplannedRoute` (the simulator path) for both valid and invalid station names (confirm `UnresolvedStationError`/`NoRouteFoundError` are thrown appropriately).
   - Whatever JSON-schema validator gets built in Phase 3 — valid response passes, malformed response throws.

**Acceptance check:** `npm test` runs clean; coverage should clearly hit the graph/matcher/parser modules since those are where all the real logic now lives.

## Phase 5 — Product features

**Priority within this phase (do this part first):** wire the disruption/rerouting feature to real-or-realistic live data instead of the 3 static presets in `src/components/DisruptionSimulator.jsx`. This is the single most product-defensible feature of the whole app (a real reroute-around-a-live-disruption story beats a static planner), so it's worth the most effort here. Concretely:
   - Even a mock endpoint that *behaves* like a real live-status feed (e.g. `api/service-status.js` returning a JSON list of currently-disrupted node/route ids, refreshed periodically or randomly) is a meaningful upgrade over hardcoded presets — it demonstrates the architecture without requiring a real operator data feed.
   - The existing `src/lib/disruptionParser.js` (free-text → blocked nodes/routes) could be adapted or bypassed in favor of directly consuming structured `{blockedNodeIds, blockedRouteIds}` from this endpoint, which would actually be more robust than text-parsing.

**Then, as time allows (roughly in this order):**
1. **Geolocation-based nearest-station detection** for trip origin — use the browser Geolocation API, then find the nearest node in `src/lib/transitGraph.js`'s graph by lat/lng (note: not all nodes currently have `lat`/`lng` — only `water_metro.jetties` do in `data.json`; metro stations and feeder stops don't. Adding coordinates for metro stations at minimum would be needed for this to work well).
2. **Persisted trip history** beyond the single most-recent journey (currently only the last journey is preserved for offline reopening, per the README's PWA description — check current `localStorage` usage for the exact mechanism before extending it).
3. **Accessibility pass** — ARIA labels, keyboard navigation — across `Home.jsx`, `Itinerary.jsx`, `DisruptionSimulator.jsx`, since this is a public-facing PWA and currently has no explicit accessibility work done.

**Also revisit here if not already handled:** the `Eloor Jetty` unreachable-node gap noted above.
